## Introduction

The Credential Rotation Automation is an enterprise-grade Ansible-based solution designed to automatically rotate service account passwords for vManage and ServiceNow integrations stored in CyberArk. This automation ensures continuous security compliance by enforcing a 30-day password rotation policy while maintaining zero-downtime operations and coordinating with EKMS (Enterprise Key Management System) teams.

### Key Highlights

- **Automated Rotation**: Zero-touch password rotation every 30 days
- **CyberArk Integration**: Secure password generation and storage via PAM
- **Multi-System Support**: vManage and ServiceNow credential rotation
- **EKMS Coordination**: Automated notification and acknowledgement with EKMS teams
- **Zero Downtime**: Seamless rotation without service interruption
- **Complete Audit Trail**: Full tracking in ServiceNow with evidence artifacts
- **Validation**: Post-rotation connectivity verification across all systems
- **Rollback Capability**: Automatic rollback on failure with Change update and alerts
- **Observability**: Comprehensive logging without exposing plaintext passwords

### Document Purpose

This wiki serves as the comprehensive knowledge base for:
- **Security Teams**: Understanding rotation policies and compliance
- **Operations Teams**: Managing day-to-day rotation operations
- **Automation Engineers**: Maintaining and enhancing the solution
- **Auditors**: Reviewing security controls and audit trails

## What is Credential Rotation?

### Definition

Credential rotation is the process of systematically changing passwords or access credentials at regular intervals to minimize the risk of unauthorized access from compromised credentials.

### Rotation Scope

This automation rotates credentials for:

1. **vManage Service Account**
   - Account: `vmanage_automation`
   - Purpose: API access for LI automation
   - Stored in: CyberArk Safe `vManage_Credentials`
   - Rotation: Every 30 days

2. **ServiceNow Integration Account**
   - Account: `servicenow_integration`
   - Purpose: ITSM API access
   - Stored in: CyberArk Safe `ServiceNow_Credentials`
   - Rotation: Every 30 days

### Rotation Process

```
┌─────────────────────────────────────────────────────────────┐
│                    Rotation Lifecycle                        │
└─────────────────────────────────────────────────────────────┘

Day 0: Password Created
  ↓
Day 1-29: Password Active
  ↓
Day 30: Rotation Triggered
  ↓
  1. Generate new password (CyberArk CPM)
  2. Update target system (vManage/ServiceNow)
  3. Update CyberArk vault
  4. Validate connectivity
  5. Create audit record
  ↓
Day 31-60: New password active
  ↓
Day 60: Next rotation cycle
```

### Solution Implementation

The credential rotation solution is implemented using **Ansible Automation Platform 2.6** with a sophisticated backend architecture that ensures reliable password rotation across vManage and CyberArk systems.

#### Core Architecture Components

**1. CyberArk Playbook Orchestration**
- Main orchestration layer that coordinates the entire rotation workflow
- Calls backend roles in the correct sequence
- Guarantees backend_finish execution even if backend_update fails
- Manages password splitting and candidate password generation

**2. Backend Roles (vManage)**
- `backend_prepare`: Validates current password and prepares for rotation
- `backend_update`: Performs the actual password update on vManage
- `backend_finish`: Cleanup and session termination

**3. Password Splitting Model**
- CyberArk password processed by splitter to produce candidate passwords
- Typically generates 1-3 candidate passwords representing current and planned states
- Handles scenarios where CyberArk CCP cache is stale
- Ensures authentication succeeds even during rotation transitions

#### Execution Flow

1. **Scheduling**: AAP 2.6 Scheduler triggers the rotation job every 30 days
2. **Change Management**: ServiceNow Standard Change template creates auto-approved change request
3. **CyberArk CCP Cache Retrieval**: Get current password from CyberArk CCP
4. **Password Splitting**: Generate candidate passwords (current + planned)
5. **Backend Prepare (vManage)**: Validate which candidate password is currently valid
6. **Password Update Sequence**:
   - **vManage API (Backend)** - Updated FIRST via backend_update
   - **CyberArk Vault** - Updated SECOND after successful backend update
7. **Backend Finish**: Cleanup session state and context
8. **Validation**: Comprehensive connectivity and functionality tests
9. **Evidence Collection**: Logs and artifacts attached to ServiceNow change
10. **Change Closure**: ServiceNow change closed with success/failure status

#### Password Splitting Model

The password splitting model solves critical synchronization challenges:

**Problem Scenarios**:
1. **Stale CCP Cache**: Password rotated but CyberArk CCP returns old value
2. **Failed CyberArk Update**: Backend updated successfully but CyberArk update failed

**Solution**:
```yaml
# CyberArk password: "CurrentPassword123!"
# Splitter produces candidate passwords:
candidate_passwords:
  - "CurrentPassword123!"      # Index 0: Current password
  - "PlannedPassword456!"      # Index 1: Planned password (if exists)
  - "FallbackPassword789!"     # Index 2: Fallback (if exists)
```

**Backend Prepare Logic**:
```python
for index, password in enumerate(candidate_passwords):
    if authenticate_to_vmanage(password):
        backend_password_index = index  # Store successful index
        break  # Stop trying further passwords
else:
    fail("No candidate password worked")
```

**Why This Works**:
- If CyberArk CCP is stale, the "planned" password (index 1) will be the actual current password
- If backend update succeeded but CyberArk update failed, the "planned" password is the actual backend password
- All playbooks using CyberArk passwords must implement the same splitting logic

#### Backend Responsibilities

**Task: backend_prepare**

**Purpose**: Validate connectivity and determine current password

**Inputs**:
```yaml
backend_password_split:  # List of candidate passwords
  - "{{ candidate_password_0 }}"
  - "{{ candidate_password_1 }}"
  - "{{ candidate_password_2 }}"
```

**Responsibilities**:
1. Connect to vManage backend system
2. Try candidate passwords in exact order provided
3. Stop at first successful authentication
4. Store successful password index in `backend_password_index` (0-based)
5. Store session state for use in backend_update and backend_finish
6. Verify system is ready for password updates
7. Fail with appropriate error if no password works

**Outputs**:
```yaml
backend_password_index: 0  # Index of working password (int or string)
vmanage_session_token: "{{ session_token }}"  # For backend_update/finish
vmanage_csrf_token: "{{ csrf_token }}"
```

**Guarantee**: If backend_prepare succeeds, backend_finish WILL be called (even if backend_update fails)

---

**Task: backend_update**

**Purpose**: Perform the actual password update on vManage

**Inputs**:
```yaml
backend_password_old: "{{ current_working_password }}"
backend_password_new: "{{ newly_generated_password }}"
```

**Responsibilities**:
1. Use session state from backend_prepare
2. Call vManage password update API
3. Update user password to backend_password_new
4. Validate the update was successful
5. Test authentication with new password
6. Fail with appropriate error if update fails

**API Call**:
```yaml
- name: Update vManage password
  uri:
    url: "https://{{ vmanage_host }}/dataservice/admin/user/password"
    method: PUT
    headers:
      Cookie: "{{ vmanage_session_token }}"
      X-XSRF-TOKEN: "{{ vmanage_csrf_token }}"
    body:
      userName: "vmanage_automation"
      password: "{{ backend_password_new }}"
    body_format: json
```

**Validation**:
```yaml
- name: Test new password
  uri:
    url: "https://{{ vmanage_host }}/dataservice/client/token"
    method: GET
    user: "vmanage_automation"
    password: "{{ backend_password_new }}"
    force_basic_auth: yes
  register: auth_test
  failed_when: auth_test.status != 200
```

---

**Task: backend_finish**

**Purpose**: Cleanup session state and context

**Responsibilities**:
1. Logout from vManage session
2. Clean up any temporary files or state
3. Release any locks or resources
4. Log completion status

**Guarantee**: Always called if backend_prepare succeeded, even if backend_update failed

**Cleanup Example**:
```yaml
- name: Logout from vManage
  uri:
    url: "https://{{ vmanage_host }}/logout"
    method: POST
    headers:
      Cookie: "{{ vmanage_session_token }}"
  ignore_errors: yes  # Don't fail on logout errors

- name: Clear session variables
  set_fact:
    vmanage_session_token: ""
    vmanage_csrf_token: ""
```

#### CyberArk Playbook Guarantees

The CyberArk orchestration playbook provides these guarantees:

1. **Ordered Execution**: Backend roles called in correct sequence (prepare → update → finish)
2. **Password Index Passing**: Only calls backend_update when backend_prepare determined current password
3. **CyberArk Update Timing**: Updates CyberArk vault AFTER successful backend_update
4. **Cleanup Guarantee**: Always calls backend_finish if backend_prepare succeeded
5. **Context Preservation**: Session state from backend_prepare available in backend_update and backend_finish

### Data Flow

```
1. Scheduler Trigger Phase
   ├─ AAP 2.6 Scheduler triggers rotation job (Day 30)
   ├─ Ansible playbook execution initiated
   └─ Execution context established

2. Pre-Rotation Phase
   ├─ Check rotation schedule (30 days elapsed)
   ├─ Verify system availability (CyberArk, vManage, ServiceNow)
   ├─ Create ServiceNow Standard Change (auto-approved)
   ├─ Receive Change ID for tracking
   └─ Backup current credential metadata

3. CyberArk CCP Retrieval Phase
   ├─ Retrieve current password from CyberArk CCP cache
   ├─ Get account ID using CyberArk admin account
   ├─ Query: GET /PasswordVault/API/Accounts?search=vmanage_automation
   ├─ Extract account ID from search results
   └─ Store current password for splitting

4. Password Splitting Phase
   ├─ Process CyberArk password through splitter
   ├─ Generate candidate passwords (typically 1-3):
   │  ├─ Candidate 0: Current password from CCP
   │  ├─ Candidate 1: Planned password (if rotation in progress)
   │  └─ Candidate 2: Fallback password (if exists)
   ├─ Store candidates in backend_password_split variable
   └─ Prepare for backend_prepare validation

5. Backend Prepare Phase (vManage)
   ├─ Receive backend_password_split list
   ├─ Try each candidate password in order:
   │  ├─ Attempt authentication with candidate 0
   │  ├─ If fails, try candidate 1
   │  └─ If fails, try candidate 2
   ├─ Stop at first successful authentication
   ├─ Store successful password index in backend_password_index
   ├─ Establish session state:
   │  ├─ vManage session token
   │  ├─ CSRF token
   │  └─ Session context
   ├─ Verify system ready for password update
   └─ Fail if no candidate password works

6. Password Generation Phase
   ├─ Generate new complex password (32 chars, FIPS 140-2)
   ├─ Password complexity requirements:
   │  ├─ 8 uppercase characters
   │  ├─ 8 lowercase characters
   │  ├─ 8 numeric characters
   │  ├─ 8 special characters
   │  ├─ No dictionary words
   │  └─ No repeating patterns
   ├─ Store as backend_password_new
   └─ Prepare for backend update

7. Backend Update Phase (vManage)
   ├─ Receive backend_password_old (from successful candidate)
   ├─ Receive backend_password_new (newly generated)
   ├─ Use session state from backend_prepare
   ├─ Call vManage password update API:
   │  └─ PUT /dataservice/admin/user/password
   ├─ Update password to backend_password_new
   ├─ Wait for password propagation (10 seconds)
   ├─ Test authentication with new password
   ├─ Validate API access and token generation
   └─ Confirm successful update

8. CyberArk Vault Update Phase
   ├─ Update CyberArk vault AFTER successful backend update
   ├─ Call: POST /PasswordVault/API/Accounts/{accountId}/SetCredentials
   ├─ Store new password in CyberArk vault (encrypted)
   ├─ Update password metadata and history
   └─ Confirm vault synchronization

9. Backend Finish Phase (vManage)
   ├─ Cleanup session state from backend_prepare
   ├─ Logout from vManage session
   ├─ Clear session tokens and context
   ├─ Release any locks or resources
   ├─ Log completion status
   └─ GUARANTEED to execute even if backend_update failed

10. EKMS Notification Phase
    ├─ Notify EKMS team of rotation completion
    ├─ Provide rotation details and timestamp
    ├─ Wait for acknowledgement
    └─ Update password/rotate credentials in EKMS systems

11. Validation Phase
    ├─ Test vManage API connectivity with new password
    ├─ Test ServiceNow API connectivity (if rotated)
    ├─ Verify all dependent automations functional
    ├─ Apply ITSM mapping and sync configuration
    └─ Confirm zero service impact

12. Evidence & Logging Phase
    ├─ Upload execution logs to ServiceNow (passed/failed)
    ├─ Attach detailed evidence (JSON artifacts, timestamps)
    ├─ Include backend_password_index in logs
    ├─ Write job outputs to observability platform
    └─ Generate success/failure statistics summary

13. Completion Phase
    ├─ Update ServiceNow Change (success)
    ├─ Archive old credentials
    ├─ Generate rotation report
    └─ Schedule next rotation (Day 60)

14. Rollback Phase (if failure)
    ├─ Backend_finish cleanup still executes
    ├─ Restore old credentials if backend_update failed
    ├─ Revert CyberArk vault if needed
    ├─ Update ServiceNow Change with failure details:
    │  ├─ Failed step information
    │  ├─ Backend_password_index used
    │  ├─ Error messages
    │  └─ Session state information
    └─ Alert operations team
```

**Key Flow Characteristics**:

1. **Password Splitting First**: Always split CyberArk password before backend operations
2. **Backend Prepare Validates**: Determines which candidate password is current
3. **vManage Updated First**: Backend update happens before CyberArk vault update
4. **CyberArk Updated Second**: Vault synchronized after successful backend update
5. **Guaranteed Cleanup**: Backend_finish always executes if backend_prepare succeeded
6. **Index Tracking**: Backend_password_index tracked throughout for troubleshooting

```yaml
rotation_due: true/false

```

- All systems must be reachable

### Step 2: CyberArk Password Rotation

**Purpose**: Generate and store new password in CyberArk

**API Call**: `POST /PasswordVault/API/Accounts/{accountId}/Change`

**Request Payload**:
```json
{
  "changeEntireGroup": false,
  "newCredentials": "auto-generated"
}
```

**Process**:
1. Trigger CPM immediate password change
2. CPM generates complex password (32 chars)
3. Password stored in CyberArk vault
4. Retrieve new password via AIM API
5. Store securely in Ansible facts (no_log: true)

**Password Complexity**:
- Length: 32 characters
- Uppercase: 8 characters
- Lowercase: 8 characters
- Numbers: 8 characters
- Special characters: 8 characters
- No dictionary words
- No repeating patterns

**Key Variables Set**:
```yaml
new_vmanage_password: "{{ encrypted }}"
new_servicenow_password: "{{ encrypted }}"
cyberark_rotation_id: "rot-20260610-050000"
```

### Step 3: vManage Credential Update

**Purpose**: Update vManage user password

**API Endpoint**: `PUT /dataservice/admin/user/password`

**Request Payload**:
```json
{
  "userName": "vmanage_automation",
  "password": "{{ new_vmanage_password }}"
}
```

**Process**:
1. Authenticate with current (old) credentials
2. Call password update API
3. Wait for password propagation (10 seconds)
4. Test authentication with new password
5. Verify API access with new credentials

**Validation Tests**:
```yaml
- Test 1: Basic authentication
- Test 2: Token generation
- Test 3: API call (GET /dataservice/system/device/vedges)
- Test 4: Session management
```

**Rollback Trigger**:
- If any validation test fails
- Restore old password immediately
- Update Change with failure status

### Step 7: Rollback (On Failure)

**Purpose**: Restore service on rotation failure

**Trigger Conditions**:
- Password update fails
- Validation test fails
- API connectivity lost
- Authentication errors

**Rollback Process**:
```
1. Detect failure point
   └─ Identify which system failed

2. Restore old credentials
   ├─ vManage: Revert to old password
   ├─ ServiceNow: Revert to old password
   └─ CyberArk: Mark rotation as failed

3. Validate rollback
   ├─ Test old credentials work
   └─ Verify service restored

4. Update ServiceNow Change with Failure Status
   ├─ Include failure details
   ├─ Link to Change record
   └─ Assign to operations team

5. Alert operations
   ├─ Email notification
   ├─ Slack/Teams alert
   └─ PagerDuty (if critical)

6. Generate failure report
   └─ Include diagnostics for troubleshooting
```

**Change Update Payload (Failure)**:

- **Audit Logging**: All actions logged

## FAQ

### Q1: How often are credentials rotated?
**A**: Every 30 days automatically. Emergency rotations can be triggered manually.

### Q2: What happens if rotation fails?
**A**: Automatic rollback restores old credentials. ServiceNow Change updated with failure status. Operations team alerted.

### Q3: Is there any service downtime during rotation?
**A**: No. Rotation is designed for zero-downtime operation.

### Q4: How are new passwords generated?
**A**: CyberArk CPM generates complex 32-character passwords automatically.

### Q5: Can I see the new password?
**A**: No. Passwords are never displayed or logged. Only stored encrypted in CyberArk.

### Q6: What if I need to rotate credentials immediately?
**A**: Execute manual rotation playbook with emergency flag.

### Q7: How do I verify rotation was successful?
**A**: Check ServiceNow Change record and AAP job logs.

### Q8: What systems are affected by rotation?
**A**: Only vManage and ServiceNow integration accounts. No impact to other systems.
